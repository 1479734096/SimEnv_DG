## 4. 历史失败根因

### 4.1 失败运行

- **运行目录**：`SimEnv/results/runs/20260711_124922_seed_42/`
- **正确识别**：1/6
- **返航结果**：成功，但探索收益极低
- **coverage_ratio**：0.517

### 4.2 异常链

```
goal_reached
→ path cleared
→ 下一 tick 重新选择当前附近同一区域目标
→ 实际位移接近零
→ 重复约 1093 次
→ 浪费约 110 秒
```

### 4.3 详细信息

- **时间范围**：仿真时间约 93.4s ~ 204.1s
- **机器人位置**：约 `(-5.791, 13.378)`，航向约 2.375rad
- **反复选中的目标坐标**：`(-6.05, 13.55)`
- **机器人到目标距离**：约 0.31m
- **规划路径长度**：约 0.38m
- **小于控制器 goal_tolerance**：0.35m，因此控制器立即判定到达并清空路径
- **相关日志**：`SimEnv/results/runs/20260711_124922_seed_42/logs/danger_search.log`
- **分歧分析文档**：`results/golden_candidate_20260711_132738/divergence_analysis.md`

### 4.4 根本原因

任务层缺少对“反复选择同一近邻目标但无实际进展”的监督。控制器按 `goal_tolerance` 正确判定到达，但 frontier 选择器不断返回几乎相同的目标，形成高频空转。

## 5. ProgressMonitor 当前完成程度

### 5.1 已实现的代码

- 新增内部类 `_ProgressMonitor`，位于 `SimEnv/src/danger_search/danger_search/mission_manager.py`。
- 功能：
  - 记录近期选中的目标位置（`record_selection`）。
  - 记录机器人位姿历史（`record_pose`）。
  - 检测同一区域内目标被反复选中且实际位移极小（`check_degenerate`）。
  - 对触发区域设置短期 cooldown（`start_cooldown` / `is_cooled` / `filter_frontiers`）。
  - 限频日志（`should_log`）。
- 在 `_tick_explore()` 中集成：
  - 每次进入无路径分支时，先过滤 cooldown 区域。
  - 若检测到退化循环，清除当前路径，尝试选择空间上不同的 frontier。
  - 若无其他 frontier，交由现有 door-approach / probe / no-frontier-scan 流程处理。
  - **不直接返航，不立即换层**。

### 5.2 计划但尚未实现的部分

- Layer 1 源头过滤：在目标交给控制器前，不根据 information_gain 或 unknown 邻格提前拒绝。
- 原地 observation / probe：检测到近邻有价值目标时，尚未实现有限转向或 unknown-space probe。
- 复杂区域切换策略：未实现多区域权重重分配或动态区域打分。
- 真实历史失败链的端到端复现与验证。

### 5.3 已通过的单元测试

- `test_progress_monitor.py`：7/7 通过
  - 同一区域近邻目标反复 goal_reached 且无移动时触发 cooldown
  - 目标坐标略有变化仍能识别为同一区域
  - 机器人持续移动时不误触发
  - 正常连续到达多个相邻 frontier 时不误判
  - cooldown 后可以选择其他区域
  - cooldown 到期后原区域可重新评估
  - 局部循环不会直接导致返航
- **重要说明**：这 7 个测试使用构造数据验证 `_ProgressMonitor` 的内部状态机；**未覆盖** `20260711_124922_seed_42` 的真实日志回放，也未验证监督器在真实 Gazebo 退化链中的介入时机。

### 5.4 尚未完成的测试

- **真实历史失败链的复现测试**：单元测试使用构造数据，未使用 `20260711_124922_seed_42` 的实际日志回放。
- **Gazebo 中主动触发退化循环的测试**：目前尚未在真实仿真中观察到 ProgressMonitor 被触发（`20260711_152204_seed_42` 中 `progress_monitor_events=0`）。
- **多 seed 稳定性测试**：仅 seed 42 完成一次成功长时运行。

### 5.5 是否在真实 Gazebo 中触发过

- **否**。最新成功运行 `20260711_152204_seed_42` 中未触发。
- 这本身是好现象（说明退化循环未出现），但也意味着监督器的真实恢复路径尚未被端到端验证。

### 5.6 已知误判风险

- 如果机器人在真实窄通道或门口附近需要多次微调（小位移、同一区域），可能被误判为退化循环。
- cooldown 区域半径基于 `goal_tolerance * 1.5`（约 0.525m），若 legitimate frontier 恰好落在该半径内，可能被错误跳过。
- 当前实现未区分“控制器正在执行有效路径但目标很近”和“目标很近但执行无效”：统一依赖位移窗口判断。

### 5.7 当前最可能存在的 bug

- **未验证路径**：退化触发后的重选择路径只测试了 `select_frontier` 返回非空的情况；若所有 frontier 都被 cooldown，则进入现有 no-frontier 流程，该分支在真实场景中的行为未验证。
- **日志限频副作用**：`should_log` 更新 `_last_log_time`，若长时间未触发，首次触发时仍会立即记录，但后续 5s 内的事件被合并，可能丢失中间诊断信息。
- **pose 历史未与 controller STUCK 联动**：ProgressMonitor 只看 odom 位移，不直接读取 controller 的 `stuck_elapsed` 或 `recover_count`。

### 5.8 下一位模型应该保留、删除或重写哪些部分

- **保留**：`_ProgressMonitor` 类结构、单元测试、`_tick_explore` 中的集成框架。
- **建议重写/增强**：
  - 增加基于真实历史日志 `20260711_124922_seed_42` 的回放测试或集成测试。
  - 将 controller 的 `stuck_elapsed` / `recover_count` 纳入监督信号。
  - 在检测到退化后增加一次显式原地转向或 sensor 观测，确认无新增地图信息再 cooldown。
- **不建议立即删除**：当前实现是无害的（未触发时行为等价于无监督器），删除不会改善问题但会移除安全网。
