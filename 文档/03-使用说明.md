## 一、使用范围

本说明用于在比赛提供的仿真环境中部署和运行危险源自主搜索系统。系统通过公开的机器人状态、传感器、导航和建筑交互接口执行任务，不使用隐藏地图、真值坐标或未公开控制通道。

运行前应确认仿真环境已由有权限的人员启动。本文只描述被测系统的构建、启动、监控和结果导出流程，不包含启动、停止或重置 Gazebo 仿真的操作。

## 三、部署步骤

### 3.1 获取并进入工作空间

在项目根目录打开终端，进入比赛工作空间。以下命令中的路径应按实际安装位置调整：

```bash
cd /home/xbh/tzb26/codeDG
```

### 3.2 加载基础环境

先加载比赛或系统要求的中间件环境，再加载本工作空间。具体环境脚本以现场配置为准：

```bash
source /opt/ros/<发行版>/setup.bash
source install/setup.bash
```

若当前工作空间尚未构建，执行：

```bash
colcon build --symlink-install
source install/setup.bash
```

构建失败时，应先记录完整错误日志并核对中间件版本、依赖工作空间和编译器版本；不要在比赛环境中随意升级系统依赖。

### 3.3 启动前检查

执行系统前，依次确认：

1. 仿真环境已运行，机器人模型与场景加载完成。
2. 传感器话题、机器人状态和导航服务可被当前终端发现。
3. 当前终端加载的是与被测代码一致的工作空间。
4. 结果目录可写，且本轮测试编号已经记录。
5. 双屏显示时，将仿真窗口置于一个屏幕，将终端、日志或监控窗口置于另一屏幕，避免相互遮挡。

## 四、启动步骤

### 4.1 启动系统节点

在新的终端加载环境后，按项目实际入口启动任务系统：

```bash
cd /home/xbh/tzb26/codeDG
source install/setup.bash
ros2 launch <软件包名> <启动文件名>.launch.py
```

`<软件包名>` 和 `<启动文件名>` 应以仓库当前 README、启动文件或赛前配置为准。启动完成后，终端应输出配置加载、接口连接和任务状态初始化信息；出现接口缺失、时间不同步或定位异常时，不应强行开始任务。

### 4.2 执行自主任务

待系统显示“就绪”或等价状态后，通过项目定义的任务触发方式进入自主模式。自主模式下，机器人依次执行建图、探索、危险源复核、建筑交互和返航，操作员应只观察状态和记录异常，不干预路径或目标结果。

> 【图 4-1 待补：系统进入自主探索后的终端状态与仿真画面。】

### 4.3 手动模式与模式切换

手动模式仅用于赛前接口验证、姿态检查和故障恢复。切换模式前必须确认机器人处于安全位置，且清楚当前导航任务是否已取消。模式切换的具体按键或服务调用以当前代码实现为准；不得将手动控制结果计入自主测试成绩。

### 4.4 任务结束与结果导出

系统完成返航或进入失败结束状态后，保存以下材料：

1. 危险源结果文件及其生成时间。
2. 本轮终端日志与错误日志。
3. 地图、轨迹、危险源确认和返航的截图。
4. 测试编号、随机种子、场景名和代码版本。

将上述信息填写至《系统测试报告》的原始测试记录单。未完成返航、人工接管或中途重启的轮次，应标注为异常轮次。

## 五、程序结构

项目代码通常按“接口适配、感知地图、任务决策、执行输出、测试工具”组织。实际文件名称以仓库为准，建议从以下入口定位：

```text
codeDG/
├── src/                 任务系统源代码
├── launch/              启动文件
├── config/              参数与场景配置
├── scripts/             辅助脚本
├── logs/                运行日志（运行后生成）
├── results/             结果文件（运行后生成）
└── 文档/                 技术、测试、使用和论文文档
```

| 模块 | 主要职责 | 运行观察点 |
|---|---|---|
| 接口适配 | 接收状态/传感器，调用导航和交互接口 | 话题时间戳、服务返回值 |
| 地图规划 | 栅格更新、前沿生成、目标评分 | 地图状态、候选点、路径 |
| 目标识别 | 候选检测、深度校验、坐标融合 | 候选数量、确认结果、置信度 |
| 任务管理 | 状态切换、超时、返航预算与异常恢复 | 当前状态、失败原因、剩余时间 |
| 结果输出 | 保存目标清单、日志和证据索引 | 文件完整性、任务编号 |

## 六、运行监控与故障处理

| 现象 | 可能原因 | 处理建议 |
|---|---|---|
| 系统未进入就绪状态 | 环境未加载、接口缺失、时间不同步 | 核对环境脚本和接口可用性，保存启动日志 |
| 机器人原地等待 | 定位健康检查未通过或无可达前沿 | 检查位姿、点云与地图更新状态 |
| 重复前往同一位置 | 失败目标未被冷却或地图更新不足 | 检查前沿记录和导航反馈日志 |
| 目标频繁出现又消失 | 深度无效、阈值敏感或观测不足 | 检查 RGB-D 对齐和多帧确认条件 |
| 门/电梯交互超时 | 接近位置不合适、状态反馈未到达 | 保留时序日志，进入恢复流程后再分析 |
| 无结果文件 | 任务异常退出或目录不可写 | 检查退出原因、目录权限和磁盘空间 |

遇到异常时，优先保存终端输出、任务日志和截图，再执行现场既定的恢复流程。不要为了获得单次成功结果而删除失败日志或手工修改输出数据。

## 七、注意事项

1. 每次测试只使用一个明确的代码版本和参数组，修改参数后应重新编号。
2. 危险源坐标、覆盖率和耗时必须由本轮日志或结果文件支撑，不得凭观察填写。
3. 运行期间避免占用同一接口的其他控制节点，以免产生指令冲突。
4. 图像和录屏应包含任务编号或系统时间，便于与测试表对应。
5. 真实机器人部署前，须额外完成急停、速度限制、相机标定、通信中断和地面适应性测试；仿真通过不等同于真实环境可直接运行。
